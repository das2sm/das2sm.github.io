Reproducing SparseOcc on nuScenes

March 2026  ·  ACSI Laboratory, Feng Chia University
3D perceptionDockerCUDAoccupancy prediction

This one was almost entirely an exercise in environment engineering — and it taught me something no course does: published research code frequently does not run.

Objective

Before starting on closed-loop planner safety, I wanted a state-of-the-art 3D occupancy baseline as a perception foundation — both to understand the representation the rest of my research would eventually build on, and to prove to myself I could take a published paper and get its exact numbers back out of my own environment.

The dependency wall

SparseOcc's dependency stack is pinned to mmcv-full==1.6.0 and mmdet3d==1.0.0rc6, which in turn require CUDA 11.8 and PyTorch 2.0. That's a coherent, working stack — on the hardware it was written for. The lab's RTX 5070 Ti is a Blackwell-architecture card with compute capability sm_120, which CUDA 11.8 has no idea exists.

I tried every path through this I could think of:

  • CUDA 11.8 in Docker — the custom CUDA extensions compiled without error, but failed at inference time with no kernel image is available for execution on the device. The compiled kernels simply contained no code for Blackwell.
  • CUDA 12.8 rebuild — supports sm_120, but mmcv-full==1.6.0 refuses to compile against PyTorch 2.7+.
  • Building mmcv from source in Conda — same wall, different door.

The conclusion was structural, not a personal failure: there is no clean intersection between SparseOcc's dependency versions and Blackwell hardware. The code predates the GPU architecture by roughly two years, and no amount of flag-tweaking closes that gap.

Lesson

The newest hardware in the room isn't always the right hardware for the job. I diagnosed the incompatibility clearly, stopped trying to force it, and moved to the RTX 3090 (sm_86), which the original stack fully supports.

Building something reusable

Once I'd committed to the 3090, I built a reproducible Docker image with the complete working stack and precompiled CUDA kernels, and pushed fixes ahead of the official repository — environment validation checks, and stripped-out compilation targets for architectures nobody in the lab was using, to keep build times sane.

This turned out to be one of the most quietly useful things I built all six months. Environment reproducibility is invisible when it works and catastrophic when it doesn't — nobody notices the Docker image until the day they desperately need it to just build cleanly on a fresh machine.

Result

MetricResult
RayIoU (ResNet-50 backbone, nuScenes)0.368
Inference latency62.5 ms
Throughput16.0 FPS (RTX 3090)

0.368 RayIoU matches the published benchmark. Reproducing a result exactly is a genuinely satisfying kind of confirmation — it means the environment, the data pipeline, the model, and the evaluation code are all correct at the same time, which is a lot of things that all have to be right simultaneously for the number to come out clean.

I generated top-down BEV semantic occupancy maps from the model and presented the paper and results to the lab.

Why this didn't end up in the final research direction

I didn't end up using SparseOcc for the closed-loop safety work that followed. Two reasons: getting SparseOcc and SparseDrive to coexist in one environment introduced its own dependency conflicts I didn't want to keep fighting, and using privileged occupancy directly from CARLA's simulator state removes sensor and perception noise as a variable entirely — which mattered for isolating the specific question the later intervention study was asking. Learned occupancy, including feeding SparseOcc's actual predictions into that pipeline, is future work.
